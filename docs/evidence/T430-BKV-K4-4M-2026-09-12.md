## Workload

- pages: 4,000,000
- signature width: 256 bits
- Hamming threshold: 96
- warmup queries: 5
- measured repetitions: 25
- seed: 1
- logical Boolean payload: 1,024,000,000 bits = 128,000,000 bytes ≈ 122.07 MiB
- representation: contiguous flat packed `u64` signatures
- scalar candidate oracle checked by the benchmark before timing

This payload is larger than one socket's 40 MiB LLC, so it is the first campaign in this series that deliberately crosses from an LLC-sized workload into a DRAM-relevant regime.

## Immediate observations

1. Scaling improves substantially once the payload exceeds the single-socket LLC regime. The 16-worker point reaches 8.46× speedup versus one worker.
2. 8 → 16 workers improves median latency by about 32.0%.
3. 16 → 32 workers is effectively flat: 32 workers are about 0.39% slower than 16.
4. 64 SMT threads regress sharply: median latency is about 63.5% worse than the 16-worker point.
5. The 32-worker run used CPU 0-31 with interleaved memory across both NUMA nodes. That placement can force each socket to consume non-local pages and therefore is **not** equivalent to a first-class Boolean-KV design with socket-local shards.

## Interpretation boundary

These measurements support the engineering hypothesis that worker count must be selected as a function of payload size and placement. They do **not** yet establish that the second socket is useless, nor that 16 workers are globally optimal. The next experiment must distinguish:

- one-socket local DRAM;
- two-socket interleaved DRAM;
- two socket-local Boolean-KV shards scanned independently and merged;
- SMT only after physical-core scaling is understood.
