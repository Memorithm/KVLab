## Observations

1. Unlike the 1M and 4M campaigns, the ~0.954 GiB working set continues to benefit from the second socket: 32 workers reduce median latency by ~24.6% relative to 16 workers.
2. SMT also remains beneficial at this size: 64 logical CPUs reduce median latency by ~9.3% relative to 32 physical-core workers and by ~31.6% relative to the 16-worker single-socket point.
3. Scaling efficiency still declines with worker count, so the gain is sublinear and consistent with a memory-bandwidth / synchronization-limited regime rather than compute-linear scaling.
4. The 32/64-worker points use interleaved allocation. They do **not** yet establish that interleaving is optimal for BKV. The next experiment must compare it with two socket-local shards, each scanned only by its local physical cores, followed by deterministic candidate merge.
5. No end-to-end attention speedup or quality claim follows from this systems-only synthetic random-control benchmark.

## Next falsifiable comparison

For the same 32M logical dataset, compare:

- single socket, node-0-local, 16 workers;
- current 32-worker interleaved baseline;
- two independent socket-local 16-worker shards with the query replicated to both sockets and deterministic merge;
- optional SMT within each local shard only after the physical-core result.

Primary decision metric: end-to-end query latency including shard launch and merge, with exact candidate-set equality against the monolithic oracle. Secondary metrics: logical bytes scanned/s, local/remote NUMA traffic where measurable, merge cost, and efficiency per physical core.
